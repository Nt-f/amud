# Deploying amud.page (landing page and web app)

`web-dist/` is the **precompiled** site, made by `tool/build_web.sh` (not
kept in git):

- `/` is the static landing page, from `landing/` (`index.html`, `og.png`,
  `robots.txt`, `sitemap.xml`, and a `sw.js` that retires the service worker
  of the app's old home at the root).
- `/app/` is the web app (PWA). It's fully self-contained: all Sefaria
  texts, rules, fonts and the renderers are bundled. Nothing is loaded
  from Sefaria or Google's CDN at runtime.
- The app is built twice (`flutter build web --wasm`): browsers with WasmGC
  (Chromium-based ones; Flutter leaves Firefox and Safari off for now) run
  `main.dart.wasm` with the skwasm renderer, the rest fall back to
  `main.dart.js` with CanvasKit. Flutter's loader picks one per browser. No
  special headers are needed: without cross-origin isolation skwasm runs
  single-threaded.

The app lived at `/` before 0.4. Old links like `/#/zmanim` and home-screen
installs are sent to `/app/` by a script on the landing page, and the old
root service worker removes itself and its caches on the next visit.

## Docker

`docker build` compiles the app from source (in a Flutter SDK image) and
serves it with nginx:

    docker build -t flutter-siddur .
    docker run -d -p 8088:8088 flutter-siddur    # http://localhost:8088
    # or
    docker compose up -d --build

Build options:

    docker build --build-arg SYNC_SEFARIA=1 -t flutter-siddur .      # re-download texts first
    docker build --build-arg BASE_HREF=/ -t flutter-siddur .         # the app alone at the root

The image is built from source, but `web-dist/` on disk is not touched. To
refresh it from the same build (e.g. before using `Dockerfile.prebuilt`):

    docker build --target web-dist --output web-dist .

To deploy the precompiled `web-dist/` without building (no Flutter SDK needed):

    docker build -f Dockerfile.prebuilt -t flutter-siddur .

## Any static host

Upload the contents of `web-dist/` to any static host (nginx, Caddy,
S3/CloudFront, Netlify, GitHub Pages, …). Serve `index.html`, `sw.js` and
`manifest.json` (at the root and under `/app/`) with `Cache-Control: no-cache`
so installed PWAs update. Serve `.mjs` as JavaScript (`main.dart.mjs` is
imported as a module, and nginx's default types don't include it) and `.wasm`
as `application/wasm`. `tool/build_web.sh` writes gzipped copies (`.gz`) of the
compiled app and renderers for hosts that serve precompressed files (nginx's
`gzip_static`). `docker/nginx.conf` is a complete example.

The app can live under another path (`BASE_HREF=/siddur/ tool/build_web.sh`),
or alone at the root without the landing page (`BASE_HREF=/`); adjust the
`/app/` locations in `docker/nginx.conf` to match.

HTTPS is required for installation and offline use (localhost is exempt).

## PWA / offline

- Installable: web manifest with icons and shortcuts to Siddur, Zmanim and Torah.
  Its `id` stays `/` so installs from before the move are the same app;
  `start_url` and `scope` are the app's folder.
- Offline-first: `sw.js` (generated by `tool/gen_service_worker.dart`)
  precaches the app shell (under `/app/`), all 67 Sefaria text files and the
  one build this browser runs (Wasm and skwasm, about 10 MB, or JavaScript and
  CanvasKit, about 13 MB) on the first visit. After that the app works with no network.
- Each deployment gets a new content-hashed cache, and old caches are removed.
- `sw.js` is the **only** service worker. `web/flutter_bootstrap.js` loads
  Flutter without `serviceWorkerSettings`, and the `flutter_service_worker.js`
  that Flutter generates just unregisters itself. Two workers fighting over
  the page caused endless reloads, so don't turn Flutter's worker back on.
- `index.html` reloads once when a new `sw.js` takes over, at most once a
  minute (a `sessionStorage` guard), so an update can't loop.

## Sefaria sources on the server

The same texts are served as a static API:

- `GET /sefaria/manifest.json`: books, versions, licenses, sources.
- `GET /sefaria/<file>.json.gz`: gzip-compressed Sefaria-format JSON for each version or index.
- `GET /sefaria/`: directory listing.

Refresh texts with `dart run tool/sefaria_sync.dart` (add `--safe-licenses`
to keep only public-domain and Creative Commons versions), then rebuild.

## Rebuilding web-dist

    tool/build_web.sh

`web-dist/` is build output and isn't kept in git: build it before
deploying. A release's site is also attached to its GitHub Release as
`amud-web.zip`.

## Redeploying amud.page

amud.page is static files on Cloudflare (a Worker with static assets and no
code, which is what Cloudflare Pages now deploys as): `deploy/amud/wrangler.jsonc`.
GitHub Actions deploys it: `web.yml` (its own workflow, separate from the
app builds in `build.yml`) builds the site and runs `wrangler deploy` on every
push to master and every `v*` tag. Run by hand on another branch, it only
uploads a preview version. A tag also attaches `amud-web.zip` to the release. It needs the
`CLOUDFLARE_API_TOKEN` (account-level Workers Scripts: Edit) and `CLOUDFLARE_ACCOUNT_ID` repository secrets. The
amud.page custom domain is attached once in the dashboard (Workers → amud →
Settings → Domains & Routes); deploys leave it alone.

`landing/_headers` and `landing/_redirects` take the place of
`docker/nginx.conf`: the app-links JSON type, CORS on the Sefaria texts and
the `/sefaria/` path. Cloudflare's default `max-age=0, must-revalidate`
covers the rest. The push sidecar (`/app/api/push/`) has no place there; it
needs its own host if it is ever turned on.

To deploy from this machine instead:

    tool/build_web.sh
    npx wrangler@4 deploy --config deploy/amud/wrangler.jsonc

Installed PWAs pick up the new version the next time they're opened. The
Docker image above still works for self-hosting.

The texts and content updates are a separate site, text.amud.page: see
`content-site/README.md`.

## Android and Windows apps

These are released from GitHub Actions, not deployed here. Push a `v*` tag;
see the README's "Releasing" section.

### Google Play

The Play build is the `play` flavor: Play delivers updates, so it has no
in-app updater and no `REQUEST_INSTALL_PACKAGES` permission
(`android/app/src/play/AndroidManifest.xml`). The GitHub APK is the
`github` flavor. The Play build asks Google Play for updates
(`in_app_update`): when Play has a newer version, the home screen's update
banner offers it, and Play's own update screen installs it.

    flutter build appbundle --release --flavor play
    # → build/app/outputs/bundle/playRelease/app-play-release.aab

It must be signed with the release (upload) key; the build fails rather
than fall back to the debug key. CI also builds it on each tag as the
`amud-play` artifact (not attached to the GitHub release). Upload it to
Play by hand.

Play Console needs the privacy policy URL, `https://amud.page/privacy`
(`landing/privacy.html`), which the app links to under Settings → About.
